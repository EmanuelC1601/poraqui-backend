# Contratos API

Estado: `main` es la base única de integración. Este documento describe los contratos implementados; revisar `docs/project-status.md` para evidencia y pendientes. OpenAPI en Development: `/openapi/v1.json`.

## Identidad, permisos y comercio

- Identity API bajo `/api/auth` con bearer; bootstrap inicial `/api/auth/bootstrap-admin` requiere `Bootstrap:AdminKey` privada.
- Roles: `PlatformAdmin`, `BusinessOwner`, `DeliveryPerson`, `ExternalCourier`; policies `PlatformAdministration`, `ManageBusiness`, `DeliveryOperations`.
- Negocios en `/api/businesses`; catálogo en `/api/businesses/{id}/products`, opciones en `/api/products/{id}/option-groups` y disponibilidad en endpoints `/availability`.
- Zonas `/api/delivery-zones/active`; administración por plataforma. Negocio configura tarifas por zona y horarios semanales.
- El pedido recibe IDs, cantidades y opciones; servidor calcula precios y tarifa usando catálogo vigente. Nunca acepta precios del cliente. Persiste snapshots de artículos, opciones, pago y tarifa.
- El propietario del recurso o admin puede administrarlo; los permisos se validan sobre el negocio/pedido asociado, no solo por rol.

## Pedido, pago y entrega

- Cliente crea con `POST /api/orders`. Requiere `commandId` GUID estable por intento lógico. Repetir ID con mismo payload devuelve mismo pedido y código; payload distinto con el mismo ID da 409. La migración aditiva `OrderCreationCommandIdempotency` está integrada en PR #29.
- Cliente sube comprobante privado a `POST /api/orders/{id}/transfer-evidence` como `multipart/form-data` con `commandId` UUID y `file` binario obligatorio. Se aceptan PDF, JPEG y PNG hasta 8 MB. Devuelve 202 al aceptar o repetir un comando idéntico, 400 por archivo/solicitud inválida, 401/403 por autorización, 404 si no existe el pedido, 409 por conflicto y 413 si se rebasa el límite de petición. PR #30 requiere `commandId` en multipart y devuelve conflicto si se reutiliza con contenido/orden distinto; migración aditiva integrada. Negocio revisa pago manualmente, acepta/rechaza, inicia preparación y marca listo.
- El cliente puede cancelar mientras el pedido esté en `PendingPayment`, `AwaitingPaymentReview` o `AwaitingBusinessDecision`. Si ya subió comprobante, cancelar crea un caso `ReviewRequired` para reembolso manual; repetir la misma cancelación no duplica historial ni el caso. Tras aceptar el pedido, la cancelación del cliente se rechaza y aplican las rutas de cancelación del negocio/operación.
- OpenAPI documenta `POST /api/orders/{orderId}/cancel` con respuesta `OrderWorkflowView` (incluye `refundStatus`), errores de autorización/estado y la regla de cancelación previa a la aceptación. Las pruebas comparan todas las rutas y schemas del documento runtime con el snapshot versionado, ignorando únicamente la URL dinámica del servidor de pruebas.
- Reparto propio: admin habilita rol y negocio asigna con monto pagadero al recoger. `POST /api/orders/{id}/pickup` valida el código y registra pago negocio→repartidor por separado del pago cliente→negocio.
- Reparto externo: admin habilita perfil; courier marca disponibilidad en una zona activa; una zona inexistente o inactiva devuelve `400` y no cambia su disponibilidad (PR #43). Negocio publica oferta con origen, destino, condiciones y remuneración; courier acepta/rechaza. La aceptación cancela las demás ofertas abiertas del pedido. Un índice filtrado impide más de una oferta `Offered` por pareja pedido/courier; el despacho persiste primero las expiraciones caducadas del pedido y una colisión concurrente devuelve `409` sin duplicar (rama `feature/unique-active-external-offer`, PR pendiente). Repetir la aceptación de la misma oferta por el courier asignado devuelve el mismo código de recogida desde un valor protegido persistido; el código no se almacena en claro (PR #47). Las ofertas vencidas se marcan al consultarlas/responder y el proceso hospedado las barre cada minuto; cancelar el pedido cancela las ofertas aún abiertas. Los eventos privados `ExternalOfferAvailable` y `ExternalOfferChanged` se emiten por courier tras guardar; el cliente consulta snapshot al suscribirse o resincroniza con `SubscribeCourierOffers()` (PR #45–#46).
- Repartidor inicia recorrido eligiendo `whatsapp` o `call`; teléfono solo se revela al asignado. Confirma entrega con código del cliente. Estados e historial consultables por participantes autorizados.
- `POST /api/account/phone/verification` inicia SMS de verificación mediante Twilio Verify; `POST /api/account/phone/verification/confirm` confirma el código y solo entonces establece `PhoneNumberConfirmed`. Ambos endpoints requieren autenticación, E.164 y comparten límite de 5 solicitudes cada 10 minutos por IP. Respuesta `429` al excederlo y `503` si el proveedor no está disponible o falta su configuración privada (`TwilioVerify:ServiceSid`, `TwilioVerify:ApiKeySid`, `TwilioVerify:ApiKeySecret`). No se guarda OTP en la aplicación.
- Acciones de transición reintentables no duplican historial ni pagos. Reportes de incidentes aceptan `commandId`; reembolso es seguimiento manual, sin movimiento bancario de la API.
- Sync offline de entrega requiere `commandId`, código y hora de captura; el servidor vuelve a comprobar autorización, estado y código antes de aceptar.
- `GET /api/admin/metrics/pilot?fromUtc={utc}&toUtc={utc}`, restringido a `PlatformAdmin`. El rango predeterminado son los últimos 30 días y el máximo es 366 días; devuelve cantidad, valor bruto de pedidos, entregados/cancelados, tiempo medio de entrega, incidencias abiertas, reembolsos por revisar y conteos por estado. Importes agregan pedidos creados dentro del intervalo.

## SignalR

Hub autenticado `/hubs/orders`; `SubscribeOrder(orderId)` valida cliente, negocio, courier asignado o admin y devuelve snapshot de estado/versión. Publica `OrderChanged` después de persistir, con datos mínimos. Courier externo puede invocar `SubscribeCourierOffers()` con rol `ExternalCourier`; se une a un grupo privado por usuario y recibe el snapshot actual de ofertas. Nuevas ofertas envían `ExternalOfferAvailable`; aceptación, rechazo, cancelación y vencimiento envían `ExternalOfferChanged` al destinatario afectado solo después de guardar. La aceptación también cancela las otras ofertas abiertas de ese pedido. Al reconectar se vuelve a invocar la suscripción para sincronizar; otros roles reciben error de autorización.

## Operación y límites

`GET /health/live` indica que el proceso HTTP está activo. `GET /health/ready` verifica conectividad SQL sin autenticación y devuelve 503 si no hay cadena configurada o SQL no está disponible; no aplica migraciones ni comprueba servicios externos.

No se ejecuta migración al iniciar la API. Migraciones y scripts revisables están bajo `src/Poraqui.Infrastructure/Persistence/Migrations` y `docs/sql`; las 16 migraciones de desarrollo están aplicadas, incluida la unicidad filtrada de oferta activa por courier/pedido (rama de trabajo pendiente de verificación SQL de concurrencia). Las diez restricciones SQL rechazan importes negativos, cantidades no positivas, horarios inconsistentes, disponibilidad sin zona y ofertas aceptadas sin código protegido. `ConnectionStrings__SqlServerTest` se configura en privado para una base aislada cuyo catálogo difiere del `InitialCatalog` de `ConnectionStrings:DefaultConnection`; el test loader omite las carreras si ambos nombres coinciden, aun si se usan alias de servidor distintos. Sin GPS ni distancia inferida; el proveedor Twilio Verify ya está integrado, pero el envío SMS productivo no se ha comprobado porque faltan sus credenciales privadas. No hay llamadas automáticas de WhatsApp ni pagos bancarios automáticos.
